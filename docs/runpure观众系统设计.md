# RunPure AI 观众系统设计文档 V2

## 1. 系统概述

跑步过程中，AI 模拟一群观众轮番向跑者喊话。每次触发交互时，系统从**观众角色 × 人格特点**矩阵中随机组合一个"声音"，结合跑者的实时数据与历史数据对比，生成一句有角色特征的话，通过 TTS 播报给跑者。

### 核心原则

- **每次触发随机切换角色** → 模拟真实观众席的嘈杂与丰富，不是同一个人唠叨全程
- **取消对话输入框** → 跑步中跑者不需要回应观众，保持沉浸
- **数据驱动** → 每句话都与当前跑步数据和历史数据强关联，不泛泛鼓励
- **赛后采访可对话** → 跑完后解锁对话框，用户选一个本场角色进行"赛后采访"
- **成长解锁** → 初始开放少量角色，跑步次数累积逐步解锁全部

### 页面结构变更

原底部导航 5 个 Tab：首页 / 历史 / 统计 / **AI** / 设置

改为：首页 / 历史 / 统计 / **观众席** / 设置

| 路由 | 页面 | 说明 |
|------|------|------|
| /audience | 观众席主页 | 替换原 /ai，含金句墙、固定粉丝团、角色图鉴 |
| /tracking | 运动中（不变） | 新增观众弹幕层 + 跑前状态选择 |
| /tracking/result | 跑步完成（扩展） | 新增"赛后采访"入口 |
| /audience/interview | 赛后采访 | 选角色后进入对话界面 |
| /ai-settings | AI 服务配置（不变） | 设置页进入 |

## 2. 角色矩阵

### 2.1 观众角色（7 种）

决定"说话的立场和动机"——这个观众为什么关注你的跑步。

| 角色 | 代号 | 核心特征 | 关注点 | 解锁条件 |
|------|------|----------|--------|----------|
| 尖叫粉 | `SCREAMING_FAN` | 情绪化狂热支持者，无条件应援 | 跑者的每一步都是伟大的 | **初始解锁** |
| 数据狂人 | `DATA_NERD` | 理性至极端，所有判断基于数据模型 | 配速偏差、统计异常 | **初始解锁** |
| 亲友后援会 | `FAMILY_CREW` | 家人朋友，情感优先 | 安全、健康、有没有吃早饭 | **初始解锁** |
| 佛系观赛组 | `ZEN_VIEWER` | 温和包容，关注跑步本身 | 过程而非结果，呼吸、风景 | **初始解锁** |
| 赌徒 | `GAMBLER` | 押注跑者成绩，数据波动引发激烈情绪 | 目标完成率、能否破PB | 累计 **10 次**跑步解锁 |
| 显微镜侠 | `NITPICKER` | 专挖黑历史，放大最差数据 | 历史最差成绩、掉速段 | 累计 **20 次**跑步解锁 |
| 影子对手团 | `RIVAL_FAN` | 其他跑者的支持者，借数据贬低跑者 | 跑者弱项与假想对手的强项对比 | 累计 **30 次**跑步解锁 |

> **设计意图：** 初始 4 个角色覆盖"热情/理性/温情/佛系"四种基础体验，新手不会一上来就被毒舌吓跑。随着跑步次数增加，跑者已经有足够的历史数据和心理准备来接受更"刺激"的角色。赌徒、显微镜侠、影子对手团需要丰富的历史数据才能发挥最佳效果。

### 2.2 人格特点（5 种，全部初始可用）

决定"说话的腔调和风格"——这个观众怎么说话。

| 人格 | 代号 | 语言风格 | 典型句式 |
|------|------|----------|----------|
| 毒舌损友 | `SAVAGE` | 犀利讽刺，以贬损表达关心 | "就这？""上次你可是……" |
| 热血教练 | `HYPE_COACH` | 激情澎湃，感叹号密集 | "冲啊！""这才是你！" |
| 诗意文青 | `POET` | 文艺婉约，善用意象 | "风刚好托着你的步伐" |
| 逗逼老炮 | `CLOWN` | 无厘头幽默，冷笑话不断 | "以这个速度，外卖小哥都追不上你" |
| 冷面解说 | `COMMENTATOR` | 正经体育解说腔，客观中带节奏感 | "选手目前处于第三公里……" |

### 2.3 组合矩阵

已解锁角色 × 全部人格 = 可用组合池。初始 4×5=20 种，满级 7×5=35 种。

**部分典型组合效果：**

| 组合 | 效果描述 |
|------|----------|
| 数据狂人 × 毒舌损友 | 用冰冷数据精准打击："配速5'47，比你上周均值慢了12秒。退步得很稳定啊。" |
| 数据狂人 × 诗意文青 | 把数据写成诗："5'20的节拍器，每一步都踩在标准差的一个σ之内。" |
| 尖叫粉 × 热血教练 | 歇斯底里的鼓励："啊啊啊啊你太强了！这个配速简直炸裂！冲！" |
| 尖叫粉 × 逗逼老炮 | 疯狂但搞笑："哥你跑得我手机都快拿不稳了，等下我发弹幕！" |
| 显微镜侠 × 毒舌损友 | 双重暴击："三周前那次3公里跑了22分钟，今天看来要破最差纪录。" |
| 显微镜侠 × 冷面解说 | 一本正经挖黑料："回顾选手历史数据，上月第三周出现了明显的训练空窗期。" |
| 佛系观赛组 × 诗意文青 | 极致治愈："不用看表，风知道你跑了多远。" |
| 佛系观赛组 × 逗逼老炮 | 佛系搞笑："快慢都行嘛，反正地球也在转，站着不动也算运动。" |
| 赌徒 × 热血教练 | 热血押注："我押你今天能破5'30，别让我输啊兄弟，冲起来！" |
| 赌徒 × 毒舌损友 | 赌输了的愤怒："我押你能跑进25分钟的，现在看来我的钱要打水漂了。" |
| 影子对手团 × 冷面解说 | 解说式贬低："目前这个配速，在本周同距离跑者中大概排在中下游。" |
| 影子对手团 × 逗逼老炮 | 搞笑挑衅："隔壁老王昨天同样距离比你快两分钟，他还是穿拖鞋跑的。" |
| 亲友后援会 × 诗意文青 | 温情满满："你跑步的样子真好看，像小时候追风筝。" |
| 亲友后援会 × 毒舌损友 | 亲人式嫌弃："你妈让我问你穿秋裤了没。" |

## 3. 今日状态（跑前选择）

### 3.1 状态定义

跑前选择一个状态，影响角色抽取的概率权重。界面：一排图标卡片，一秒点完。

| 状态 | 代号 | 图标 | 效果 |
|------|------|------|------|
| 激励我 | `MOTIVATE` | 🔥 | 偏向正面激励、打鸡血、强调进步 |
| 安慰我 | `COMFORT` | 🫂 | 偏向温暖包容、淡化数据压力 |
| 刺激我 | `PROVOKE` | 😈 | 偏向毒舌激将、挖黑历史、不留情面 |
| 逗我笑 | `AMUSE` | 😎 | 偏向幽默搞笑、冷笑话、无厘头 |
| 专注跑 | `FOCUS` | 🎯 | 最少干扰，仅关键节点触发 |

### 3.2 权重矩阵

不是硬性过滤，而是概率权重。正如真实观众席，嘘声中也会有人喊加油。

**角色权重（数值越高被抽中概率越大）：**

| 角色 \ 状态 | MOTIVATE | COMFORT | PROVOKE | AMUSE | FOCUS |
|------------|----------|---------|---------|-------|-------|
| 尖叫粉 | **2.0** | 1.0 | 0.3 | 1.0 | 0.3 |
| 数据狂人 | 1.0 | 0.5 | 1.0 | 0.8 | **2.0** |
| 亲友后援会 | 1.5 | **2.0** | 0.3 | 1.0 | 0.5 |
| 佛系观赛组 | 0.8 | **2.0** | 0.2 | 1.0 | 1.5 |
| 赌徒 | 1.5 | 0.5 | 1.5 | **2.0** | 0.5 |
| 显微镜侠 | 0.3 | 0.2 | **2.0** | 1.0 | 0.5 |
| 影子对手团 | 0.3 | 0.2 | **2.0** | 1.5 | 0.5 |

**人格权重：**

| 人格 \ 状态 | MOTIVATE | COMFORT | PROVOKE | AMUSE | FOCUS |
|------------|----------|---------|---------|-------|-------|
| 热血教练 | **2.0** | 1.0 | 1.0 | 0.8 | 1.0 |
| 毒舌损友 | 0.5 | 0.3 | **2.0** | 1.0 | 0.5 |
| 诗意文青 | 1.0 | **2.0** | 0.5 | 0.8 | 1.0 |
| 逗逼老炮 | 0.8 | 0.8 | 0.8 | **2.0** | 0.3 |
| 冷面解说 | 1.0 | 0.5 | 1.0 | 0.5 | **2.0** |

> 未解锁角色权重自动归零，不参与抽取。

## 4. 数据流设计

### 4.1 数据预处理（跑前，手机端本地计算）

跑步开始前，从本地数据库查询并生成 `RunnerProfile`，作为每次 prompt 的基础数据。

```
RunnerProfile {
  // 总览
  total_runs: int               // 总跑步次数
  total_distance_km: float      // 累计总距离
  total_duration: Duration      // 累计总时长
  streak_days: int              // 当前连续跑步天数
  days_since_last_run: int      // 距上次跑步天数

  // 最佳/最差记录
  best_pace: String             // 历史最佳配速（如 "4'32"）
  worst_pace: String            // 历史最差配速
  longest_run_km: float         // 最长单次距离
  shortest_run_km: float        // 最短单次距离
  best_5k_time: String?         // 5K 最佳成绩（如有）
  best_10k_time: String?        // 10K 最佳成绩（如有）

  // 近期趋势（近 4 周）
  weekly_distances: List<float> // 近 4 周各周跑量 [本周, 上周, ...]
  weekly_counts: List<int>      // 近 4 周各周跑步次数
  recent_avg_pace: String       // 近 4 周平均配速
  recent_avg_distance: float    // 近 4 周单次平均距离
  pace_trend: enum              // IMPROVING / STABLE / DECLINING

  // 月度统计
  month_distance: float         // 本月累计
  month_runs: int               // 本月跑步次数
  month_avg_pace: String        // 本月平均配速

  // 习惯特征
  preferred_time: String        // 最常跑步时间段（如 "晚上 20:00-22:00"）
  preferred_distance: String    // 最常跑步距离区间（如 "5-7km"）
  avg_runs_per_week: float      // 周均跑步频次
}
```

### 4.2 触发时机

| 触发点 | 条件 | 注入数据 |
|--------|------|----------|
| 开跑喊话 | 倒计时结束，正式开始 | RunnerProfile + 今日状态 + 时间/天气/节日 |
| 公里分割 | 每完成 1 公里 | 当前公里配速 vs 历史平均、vs 上一公里、vs 本次均速 |
| 5 公里节点 | 完成 5/10/15... 公里 | 阶段累计数据、与历史同距离对比 |
| 配速异常 | 当前公里配速偏离均值 > 20% | 偏离程度、方向（加速/掉速） |
| 跑步结束 | 用户按下结束 | 完整本次数据 vs 历史全维度对比 |

**短跑适配：** 距离 < 3km 时，仅触发开跑 + 每公里 + 结束，跳过 5km 节点。

### 4.3 实时数据注入（每次触发时）

```
TriggerContext {
  trigger_type: enum           // START / SPLIT_KM / SPLIT_5KM / PACE_ALERT / FINISH

  // 当前数据
  current_km: int              // 已完成公里数
  current_km_pace: String      // 当前公里配速
  current_avg_pace: String     // 本次跑步平均配速
  current_distance: float      // 当前总距离
  current_duration: Duration   // 当前总用时
  elapsed_since_last: Duration // 距上次触发的时间

  // 对比数据（手机端预计算）
  vs_last_km: String           // 比上一公里快/慢多少
  vs_history_avg: String       // 比历史平均配速快/慢多少
  vs_best_pace: String         // 与历史最佳的差距
  vs_same_distance_best: String? // 与同距离历史最佳对比（如有）

  // 分公里配速列表
  split_paces: List<String>    // ["5'20", "5'18", "5'25", ...]

  // 环境
  time_of_day: String          // "早晨" / "中午" / "傍晚" / "深夜"
  temperature: int?            // 气温（如可获取）
  weather: String?             // "晴" / "阴" / "雨" / "雪"（如可获取）
  holiday: String?             // "春节" / "中秋" / "圣诞" 等（如命中）
}
```

### 4.4 天气 / 节日彩蛋数据

手机端在跑步开始时检测环境信息，注入 TriggerContext：

**天气检测：**
- 优先读取系统天气（如 iOS WeatherKit / Android 天气 Provider）
- 无法获取时留空，prompt 中不强制引用天气
- 极端天气（高温 > 35°C、低温 < 0°C、暴雨、大风）作为特殊标记传入

**节日检测：**
- 本地维护节日日历表（农历 + 公历），跑步开始时检测是否命中
- 命中时在 prompt 中追加节日上下文，角色会自然融入节日元素

**彩蛋触发规则：**

| 条件 | 彩蛋效果 |
|------|----------|
| 下雨天跑步 | 观众喊话融入雨天意象（"雨中跑步太浪漫了" / "这雨天还出来跑，赌徒精神"） |
| 气温 > 35°C | 观众表达对高温的反应（"三十八度你还跑？我光坐着都出汗了"） |
| 气温 < 0°C | 观众关注保暖（"零下三度，你的配速比暖气升温都快"） |
| 深夜 23:00+ 跑步 | "午夜跑者"主题喊话 |
| 凌晨 5:00 前跑步 | "黎明先锋"主题喊话 |
| 春节 | "大年初X还跑步你是真卷" |
| 情人节 | "情人节不约会出来跑步，跑鞋才是真爱" |
| 中秋 | "月亮替你计圈" |
| 元旦 | "新年第一跑，数据清零重新做人" |
| 连续跑步 7 天+ | "铁人"主题 |
| 距上次跑步 > 14 天 | "归来"主题 |

## 5. 单次交互完整流程

```
┌───────────────┐
│  触发事件发生   │  （如：完成第 3 公里）
└──────┬────────┘
       ▼
┌───────────────┐
│ 手机端预计算    │  计算 TriggerContext（当前公里配速、对比数据等）
│               │  检测天气/节日彩蛋条件
└──────┬────────┘
       ▼
┌───────────────┐
│ 随机抽取角色组合 │  从已解锁角色池中，根据今日状态权重随机选 (角色, 人格)
│               │  防重复：跳过最近 5 次已出现的组合
│               │  固定粉丝团加权：用户锁定的组合权重 ×1.5（提高但不保证）
└──────┬────────┘
       ▼
┌───────────────┐
│  组装 Prompt    │  系统 prompt（角色定义 + 约束）
│               │  + RunnerProfile（历史数据）
│               │  + TriggerContext（实时数据 + 天气/节日）
│               │  + 今日状态倾向
└──────┬────────┘
       ▼
┌───────────────┐
│  调用 LLM API   │  非流式，等完整响应
│               │  超时 8 秒，失败静默跳过
└──────┬────────┘
       ▼
┌───────────────┐
│  本地持久化     │  将喊话内容 + 角色组合 + 触发数据存入 AudienceShout 表
└──────┬────────┘
       ▼
┌───────────────┐
│  TTS 播报       │  flutter_tts 语音播出
└──────┬────────┘
       ▼
┌───────────────┐
│  UI 弹幕显示    │  屏幕顶部短暂显示（角色 emoji + 文字，3-5 秒淡出）
└───────────────┘
```

## 6. Prompt 工程

### 6.1 系统 Prompt 模板

```
你正在一场跑步直播比赛的观众席上观看跑者跑步。

## 你的身份
- 观众角色：{audience_role_description}
- 说话风格：{personality_description}

## 你手中的跑者资料
{runner_profile_formatted}

## 当前比赛实况
{trigger_context_formatted}

## 今日跑者状态偏好
跑者今天希望：{mood_description}
请在保持角色特征的前提下，适当倾向这个情绪方向。

{weather_holiday_hint}

## 输出约束
- 你是观众，对跑者大喊一句话。
- 必须像真的从观众席喊出的一句话，自然、口语化、有角色感，不要像 AI。
- 长度：15-40 个汉字（TTS 友好，约 5-15 秒播报时长）。
- 必须包含至少一个具体数据引用（配速、距离、时间等），不要泛泛而谈。
- 不要用 emoji。
- 不要用标点堆砌（如连续感叹号），TTS 会逐个读出。
- 不要说"加油"这种毫无信息量的话，除非你是尖叫粉角色。
- 不要给专业训练建议，你是观众不是教练。
- 只输出喊话内容本身，不要任何前缀、角色标签或解释文字。
```

### 6.2 各角色 Prompt 片段

**观众角色描述（audience_role_description）：**

```yaml
DATA_NERD: |
  你是「数据狂人」。你对跑步数据有执念般的热爱，任何数字波动都逃不过你的眼睛。
  你用数据模型评判一切，发言必须包含精确数字。
  配速快了你会用统计指标来赞美，慢了你会用百分位来冷嘲。
  你说话像在做赛后数据报告，但嘴替了无数观众想说的话。

SCREAMING_FAN: |
  你是「尖叫粉」。你是跑者的死忠粉丝，情绪化到极点。
  配速快了你尖叫，慢了你哭着喊加油，不管数据好坏你都觉得跑者是最棒的。
  你会忽略或美化不好的数据，把每一步都说成史诗级的表现。
  你的发言充满感叹和情绪词，像亲眼看到偶像绝杀的球迷。

NITPICKER: |
  你是「显微镜侠」。你专门关注跑者最差的数据和黑历史。
  你会翻出历史最差记录来对比，放大每一个掉速的瞬间。
  你不是恶意的，更像是那种"毒舌但说的都是事实"的评论员。
  你的发言总是指向跑者最不想被提起的数据。

ZEN_VIEWER: |
  你是「佛系观赛组」。你不太关注数据，更关注跑步本身的体验。
  快慢对你来说不重要，重要的是跑者在跑、在呼吸、在感受。
  你会关注时间段、天气、跑步的节奏感，偶尔提一句数据但不执着。
  你的存在像一阵微风，让跑者放松下来。

GAMBLER: |
```

## 8. 赛后采访系统

### 8.1 概述

跑步结束后，在结果页（`/tracking/result`）提供「赛后采访」入口。用户从本场出现过的角色组合中选择一个，进入对话界面，与该角色进行"赛后访谈"式的聊天。

这是整个观众系统中**唯一有对话输入框的地方**。

### 8.2 流程

```
跑步结束 → 结果页展示本次数据
                ↓
        「赛后采访」按钮
                ↓
        角色选择面板：展示本场出现过的所有角色组合
        （显示角色 emoji + 名称 + 本场某句代表性喊话）
                ↓
        用户选择一个角色
                ↓
        进入对话界面（/audience/interview）
        - 角色以本场最后一句喊话作为开场白
        - 用户可以自由对话
        - 角色始终保持选定的 (观众角色 × 人格特点) 设定
        - 对话上下文包含完整的本次跑步数据
```

### 8.3 采访 Prompt 模板

```
你刚才在一场跑步直播比赛中作为观众观看了跑者的完整跑步过程，现在比赛结束了，跑者走过来接受你的"赛后采访"。

## 你的身份
- 观众角色：{audience_role_description}
- 说话风格：{personality_description}

## 你在比赛中的喊话记录
{shouts_during_run}

## 跑者完整数据
{runner_profile_formatted}
{final_run_summary}

## 对话规则
- 保持你的角色特征和说话风格，始终在"角色"内对话。
- 你是观众，不是教练。可以评价、调侃、赞美、质疑，但不要给专业训练计划。
- 回复控制在 2-4 句话以内，保持对话节奏。
- 可以引用你在比赛中喊过的话来延续话题。
- 可以对跑者的回复做出角色内的反应（比如赌徒关心成绩、亲友关心健康）。
- 语气自然口语化，像赛后跑道边的闲聊，不要像采访稿。
```

### 8.4 对话存储

采访对话复用现有 `ChatMessages` 表：
- `conversationId` = `interview_{sessionId}_{timestamp}`
- `sessionId` 关联本次跑步记录
- 额外字段或 metadata 存储角色组合信息

## 11. 客户端实现要点

### 11.1 角色组合随机算法

```dart
/// 根据今日状态权重 + 已解锁角色 + 固定粉丝团加权，随机抽取角色组合
(AudienceRole, Personality) pickRandomVoice({
  required MoodState mood,
  required Set<AudienceRole> unlockedRoles,
  required List<(AudienceRole, Personality)> fanTeam,
}) {
  // 1. 获取基础权重
  final roleWeights = _getRoleWeights(mood);
  final personalityWeights = _getPersonalityWeights(mood);

  // 2. 未解锁角色权重归零
  for (final role in AudienceRole.values) {
    if (!unlockedRoles.contains(role)) {
      roleWeights[role] = 0.0;
    }
  }

  // 3. 固定粉丝团加权
  for (final (favRole, favPersonality) in fanTeam) {
    roleWeights[favRole] = (roleWeights[favRole] ?? 0) * 1.5;
    personalityWeights[favPersonality] = (personalityWeights[favPersonality] ?? 0) * 1.5;
  }

  // 4. 加权随机抽取
  final role = _weightedRandom(AudienceRole.values, roleWeights);
  final personality = _weightedRandom(Personality.values, personalityWeights);

  return (role, personality);
}
```

### 11.2 防重复机制

```dart
final _recentVoices = Queue<(AudienceRole, Personality)>();
const _maxRecent = 5;  // 最近 5 次不重复

(AudienceRole, Personality) pickWithDedup({
  required MoodState mood,
  required Set<AudienceRole> unlockedRoles,
  required List<(AudienceRole, Personality)> fanTeam,
}) {
  (AudienceRole, Personality) voice;
  int attempts = 0;
  do {
    voice = pickRandomVoice(mood: mood, unlockedRoles: unlockedRoles, fanTeam: fanTeam);
    attempts++;
  } while (_recentVoices.contains(voice) && attempts < 10);

  _recentVoices.addLast(voice);
  if (_recentVoices.length > _maxRecent) _recentVoices.removeFirst();

  return voice;
}
```

### 11.3 触发频率控制

```dart
bool shouldTriggerSplit(int completedKm, double currentDistanceKm) {
  if (completedKm == 1) return true;            // 第 1 公里始终触发
  if (currentDistanceKm < 3) return true;        // 短跑每公里都喊
  if (currentDistanceKm < 10) return true;       // 中距离每公里
  if (completedKm % 2 == 0) return true;         // 长距离每 2 公里
  if (completedKm % 5 == 0) return true;         // 5 的倍数额外触发
  return false;
}
```

### 11.4 API 调用策略

| 参数 | 值 | 说明 |
|------|----|------|
| 流式 | **否** | 句子短（15-40 字），非流式延迟更低 |
| 超时 | **8 秒** | 超时则跳过本次，不阻塞跑步 |
| 失败策略 | **静默跳过** | 网络失败不提示错误，不中断跑步体验 |
| max_tokens | **80** | 约 40 个汉字足够 |
| temperature | **0.9** | 鼓励多样性和创造性 |
| 并发控制 | **互斥锁** | 上一次请求未完成时跳过新触发 |

### 11.6 解锁检查逻辑

```dart
/// 每次跑步完成后检查是否有新角色可解锁
Future<List<AudienceRole>> checkUnlocks(int totalRunCount) async {
  final newUnlocks = <AudienceRole>[];

  final unlockThresholds = {
    AudienceRole.gambler: 10,
    AudienceRole.nitpicker: 20,
    AudienceRole.rivalFan: 30,
  };

  for (final entry in unlockThresholds.entries) {
    if (totalRunCount >= entry.value) {
      final alreadyUnlocked = await _dao.isUnlocked(entry.key);
      if (!alreadyUnlocked) {
        await _dao.unlock(entry.key, totalRunCount);
        newUnlocks.add(entry.key);
      }
    }
  }

  return newUnlocks;
}
```
